# 订阅消息与虚拟支付资料

## 订阅消息：模板与字段是同一契约

源记录围绕更换 AppID 后重新申请模板和发送失败。可保留的工程检查是：目标 AppID、模板 ID、模板字段名／类型、客户端申请和服务端发送必须一致。

- 核对 `wx.requestSubscribeMessage` 的所有调用位置、后端模板配置、环境变量以及可能存在的缓存／灰度覆盖值。
- 字段名如 `thing9`、`time2` 是某个模板的键，不是固定业务字段；以后台实际模板详情为准。
- `47003 ... data.<字段>.value is empty` 可辅助定位缺项，但不应反复向真实用户发送请求来猜字段。源文“参数校验失败绝不消耗授权额度”未复核，不能作为安全重试保证。
- 一次性订阅的授权、用户选择和实际可发送次数分别核实；“accept 即必定增加一次额度”“未弹窗即正常”不能替代目标版本和账户验证。
- 权限声明、定时任务和超时按当前部署核对。时区用明确的业务时区转换，不把源文的固定 `+8` 当所有环境的唯一实现。

验收覆盖：用户明确授权、模板字段匹配、发送结果与失败分流、重复发送保护、时区和业务频率。消息文本保持真实业务目的；测试对象和发送范围需获得授权。

来源入口：[订阅消息](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/subscribe-message.html)。

## 虚拟支付：把历史沙箱现象与平台契约分开

源作者 2026-08-11 记录过：沙箱付款实际扣款、未收到发货通知而通过查单入账，以及缺 JSON Content-Type 返回 HTTP 412 的情况。这些样本不证明所有沙箱、商品模式或未来平台都相同。

**风险优先**：未确认官方当前测试机制之前，按“可能真实扣款”管理预算；资料整理不授权支付、退款或真实订单测试。沙箱回调缺失也不能推广为永久不会推送。

## 签名与订单核对线索

以下仅记旧集成方式，参数和签名需以[虚拟支付官方文档](https://developers.weixin.qq.com/miniprogram/dev/platform-capabilities/business-capabilities/virtual-payment.html)当前版本验证：

| 项目 | 旧记录 | 后续检查 |
| --- | --- | --- |
| 服务端 xpay | URI 与 JSON 请求体组成 HMAC-SHA256 签名输入 | 序列化后签名字节与实际发送一致，核对路径、头、环境与编码 |
| 请求头 | 显式 `Content-Type: application/json` | HTTP 412 还可能有其他原因；同时检查 HTTP 与业务错误 |
| 客户端 | `mode` 外层参数，`signData` 为字符串，另传 paySig／signature | 区分所选业务模式、API 版本与签名字段，不从某次报错推导全部接口 |
| 凭据 | AppKey 与 session_key 各有不同签名用途 | 仅在受控服务端处理，环境配对正确，禁止泄漏到客户端／日志／文档 |
| 订单 | 源案例 success 未返回 orderId，用 outTradeNo 查单 | 客户端成功回调不作为单独发货依据；用服务端核验的订单状态闭环 |

建议评估“可信通知 + 查单补偿”的恢复设计，发货以订单幂等状态机控制；通知验签、金额、商品、环境、订单归属逐项校验。轮询间隔、限流和终止策略按平台能力设计，不把双通道简单等同于任意次数查询。

成功退款不撤销已经交付的权益，退款和补偿也要幂等且可审计。以上是设计建议；本次没有验证签名、通知、查单、扣款或发货。
